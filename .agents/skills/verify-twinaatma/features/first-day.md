# The first day

A new person installs once, connects the hosts they chat in, brings in what another assistant already knows, and has a useful first chat. Nothing reaches their profile without their own decision in a terminal.

## Sub-features

- DAY.1. The first chat of a new vault (an empty profile and no note of the person's own) asks one plain question, once, and carries the steps the agent follows. A follow-up that is due comes before it. A vault that already holds the person's notes gets no first-run question. A section counts as filled when it holds anything below the line `init` wrote: the first approved addition is appended under that line, and the line itself is never shown.
- DAY.2. `twinaatma import` turns an assistant export or agent files into ordinary notes, withholds what the remembering policy refuses, and is safe to repeat. A source file whose own frontmatter marks it private or not to be remembered is withheld whole. A source inside the vault, or a folder that holds the vault, is refused. In a folder, a link, a file of the vault and a file with a second name (a hard link) are skipped, and each one is named. Each file is read through one open handle, and the checks are made on that handle. Import defends against an accident, not against a second program that changes files during the run (`docs/threat-model.md`). A folder with more than 200 text files is refused whole unless `--many-files` is passed. One run writes at most 500 new notes and drafts at most 12 rules; it reports what is left, and the same command continues. A rule is drafted once: a rule in the profile, in a waiting draft, or in a draft the person decided (a rejected one too) is not drafted again. Rules are compared as whole lines, and notes by their exact label and exact text. What a draft asked is kept as line digests in the signed record outside the vault (`asked_lines`), so an edited or deleted draft file changes nothing. A draft from before this field counts only while its file is unchanged; otherwise the import says that it could not be checked. Each note from a folder names its file.
- DAY.3. Rule-like lines become one profile draft. `twinaatma self review` decides every waiting draft in one sitting, in a real terminal only.
- DAY.4. `memory_search` keeps `ranked` for notes that hold every word. Notes that hold some words go in `possibly_related`, with a note that says so.
- DAY.5. A profile draft is not a note: no tool that returns notes returns a file from `People/Self-Proposals/`, decided or not. A draft is reached on purpose, by `memory_list_self_proposals` or by a read of its own path. Starter pages and templates are not offered as memory in the startup context or as `possibly_related`; a search that names a starter page on purpose still finds it. A map or index page is a starter page only under a name the toolkit writes (`_Index.md`, `_MOC_*.md`, the vault `README.md`); a map the person wrote is memory. A row in the startup context is built from a read made at that moment: a note that can no longer be read (made private, forgotten, deleted) is dropped.
- DAY.6. `setup-host --global` registers the vault for every project through the host's own command (Claude Code, Codex). `--host claude-code --write` writes the project `.mcp.json`.
- DAY.7. For Claude Code, when the registration succeeds, `--global` also merges two hook entries into the person's `settings.json` (`--no-hooks` skips them). A failed registration sets no hooks, so the hooks never point at a missing server or at another vault's server. `twinaatma hook claude-code --vault <vault>` reads the event on stdin. On `SessionStart` it prints how to use the memory server and the approved profile. On `UserPromptSubmit` it prints the saved notes that match the prompt. It changes no note and not the profile, it uses the startup-context route (which brings the search index up to date, as every memory call does), and it ends with exit code 0 and no output on every error.

## How to get to it (user POV)

`pip install`, `twinaatma init brain`, `cd brain`, `twinaatma setup-host --host claude-code --global`, `twinaatma import <file>`, `twinaatma self review`, then chat.

## Driving it with CLI and host traces

Preconditions: a new task-owned output directory. The driver sets its own `KNOWLEDGEOS_STATE_DIR`.

- Source journey. Run `python -B .agents/skills/verify-twinaatma/scripts/first_day.py --output <new-dir>`. It drives the real command line and the real MCP stdio server on a synthetic vault: init, first chat, capture, dry run, import, repeated import, review refusal, second chat, three searches, agent approval refusal, the Claude Code hook for both events, both user-level command lines, the Claude Code project file and doctor. It compares `People/Self.md` with its state right after init after every stage. It prints one PASS or FAIL line per check and writes `report.json`. It makes no model call, so it earns no host acceptance credit.
- Unit suites. `python -B -m unittest discover -s tests -p "test_first_contact.py"`, and the same for `test_import_memory.py`, `test_import_command.py`, `test_user_level_setup.py`, `test_draft_is_not_memory.py` and `test_privacy_metadata_comments.py`. A new memory tool must be placed in the table at the top of `test_draft_is_not_memory.py`.
- Owner review. `self review` needs a real console. A person runs it; the suites patch the console check and type `y`, `d` and `n`. Never answer a real approval prompt from an agent.
- Claude Code hook. `python -B -m unittest discover -s tests -p "test_claude_hook.py"` covers the hook text, the settings merge and the command. The suite moves the settings folder with `CLAUDE_CONFIG_DIR`. To see the hook in a real chat without a change to anyone's settings, write the output of `setup-host --host claude-code --global --print` (the JSON part) to a new file and start `claude --settings <that file>`. A hook entry needs the installed `twinaatma` command, so a source checkout prints the reason and sets none.
- User-level setup. The suites replace the host command with a recorder. To prove a real registration, a person runs `twinaatma setup-host --host claude-code --global` and then `claude mcp get knowledgeos`. An agent must not change the owner's host configuration without being asked, and that includes `~/.claude/settings.json`.
- Genuine host chat. Start a new session in the connected host with a fresh vault. Require the first-run question once, a capture, and after an import a grounded answer that quotes an imported note. Retain the tool trace.

## Gotchas

`ranked` staying empty for a plain question is intended; read `possibly_related`. Recall is lexical with concept clusters: a question that shares no word and no cluster with the note finds nothing ("which database" does not find a note that only says "Postgres"). The policy withholds what it recognises as a credential; it does not judge every sensitive sentence. The privacy rule fails closed: a note with a privacy key (`privacy`, `memory_privacy`, `sensitivity`, `memory_policy`) is private unless every value is one of `ordinary`, `public`, `shared`, `open`, `normal`, `none`, `low`, and a flag such as `do_not_remember` counts as set unless its value clearly says no. A value or a form the reader does not know keeps the note private, and a repeated key counts wherever it stands. `doctor` counts the marked notes. `tests/test_privacy_metadata_comments.py` holds the cases. On Windows `--global` starts the host only when its command is an `.exe`; for a script wrapper it prints the line to run. The host refuses a second registration under the same name; the message names the remove command. No hooks are set in that case; remove the server and run the command again. A person whose `claude` command is a script wrapper registers by hand and pastes the entries that `--global --print` shows. The settings merge treats an entry as its own only when the program is `twinaatma` and the arguments are exactly `hook claude-code --vault <path>`. Claude Code shares no lock for its settings file: the merge looks at the file directly before the swap, and a change made in that instant by another program cannot be seen. The prompt hook starts a new process for each prompt and checks the index, so it adds about two seconds on a small vault; the entry carries a 20 second limit, and the host drops the output of a hook that reaches it. The merge reads the settings as strict JSON: a file with comments, `NaN`, a repeated key, or a number that a rewrite would change (`1.234567890123456789`, `1e999`), and a linked file, is left unchanged and the entries are printed for a paste.
